# create-issue — 意図を起票の瞬間に確保する

Issue 駆動フローの入口。後工程（polish-issue での磨き上げ、実装）は「意図が起票時に書かれている」ことを前提にする。意図（なぜやるか・どこまでやるか・何を受け入れるか）は起票者の頭の中にしか存在せず、コードベースをいくら調査しても復元できない。逆に実装方針・対象ファイルは後から導出できる。だからこのスキルは**人間にしか答えられないことだけを聞き、それ以外を聞かない**。

## 原則

- 意図を創作しない。文脈から仮説を立ててよいが、必ず【推測】付きの選択肢として提示し、依頼者に選ばせる
- 実装方針を聞かない・求めない。依頼者が方針を語ったら「実装方針の初期仮説」として任意欄に記録し、実装者を束縛しない参考情報であることを明記する
- タイトルは目的で付ける。手段・方針を含めない
  - 良い例: 「手動編集された不正な DataLoader タスク ini を検知できるようにする」
  - 悪い例: 「ini 検証 PowerShell スクリプトを作る」
- 起票先の指定がなければ、環境変数 `ISSUE_REPO` が指すリポジトリにする。`ISSUE_REPO` が未設定なら依頼者に確認する

## 必須4項目

| 項目 | 書くこと | よくある失敗 |
|---|---|---|
| なぜやるか | 誰が・いつ・何に困っている事象 | 「X が無いのが問題」という解決策の言い換え。その場合は「X で解きたい事象は何か」を聞き直す |
| きっかけ（一次情報） | 障害ログの実物・問い合わせ・決定の場へのリンクか貼り付け | 無いのに省略する。無いなら「一次情報なし（記憶ベース）」と明記し、本文の確度を読み手に伝える |
| 何ができたら終わりか（完了条件） | 受け入れ可能な観測。機械検証できる条件（コマンド・テスト）を優先し、どの環境で検証すれば足りるかも書く | 「〜を実装したら終わり」のトートロジー。逆チェック（後述）で強度を確認する |
| 今回やらないこと・触らないこと | 隣の課題のうち手を出さないもの、触ってはいけない場所・時期（凍結・並行作業・顧客調整） | 網羅しようとして空欄になる。分かる範囲でよい。隣接問題の発見は polish-issue が担う |

**完了条件の逆チェック**: 書けたら「この条件を PASS させたまま、意図に反する成果物が作れるか」を自問する。作れるなら条件を厳密化するか、その論点を polish-issue への申し送りとして任意欄に書く。

### 事象起因の Issue では発生した事象を具体的に書く

障害や不具合など、実際に起きた出来事が起点の Issue では、「なぜやるか」と「きっかけ（一次情報）」に事象そのものを書く。リンクだけの参照では、リンク先が消えたり読み手が辿らなかったりしたときに本文が根拠を失う。

- **発生日時と環境**：例: 2026-07-25 朝、本番環境のバッチサーバ
- **観測した事実**：画面やコマンドで見えたことに加え、エラーメッセージやログは実物の抜粋を貼る
- **影響**：誰がどの作業をできなくなったか

分からない項目は創作せず ◆ スロットで依頼者に確認する。改善案やアイデアが起点で、参照すべき事象が存在しない Issue には適用しない。

## ワークフロー

1. 依頼内容から4項目とタイトルの草案を作る。埋まらない項目・推測で埋めた項目を特定する
2. 意図レベルの欠落だけを AskUserQuestion で確認する（1回最大4問。選択肢に【推測】仮説を含めて選ぶだけで済むようにする）。設計・機械レベルの疑問は聞かずに polish-issue へ委ねる
3. 本文を組み立てて提示し、依頼者の確認を得てから起票する:

   ```bash
   gh issue create --repo "$ISSUE_REPO" --title "<目的で書いたタイトル>" --body-file <草案ファイル>
   ```

4. polish-issue に回す場合は `polish` ラベルを付ける。ラベルがリポジトリに無ければ作成から提案する

### 非対話実行の場合

ループ・サブエージェント内で質問できない場合は、質問せず、回答待ち箇所を `◆[Q番号]` スロットで示した草案を返して終了する。◆ が残った草案をそのまま起票してはならない。

## 本文テンプレート

Issue Forms テンプレートは GitHub の Web UI 専用で、gh CLI や API からの起票には適用されない。AI 経由の起票では、このスキルがテンプレートの代替になる。

起票先リポジトリが `.github/ISSUE_TEMPLATE/` にテンプレートを持つ場合は、起票前にそれを読み、見出し構造と各フィールドの記入ガイド（description）に合わせる。本スキルの記述と食い違うときはテンプレート側を正とする。テンプレートはチームのレビューを経た正本であり、スキルより更新が先行しうるため。テンプレートが無い場合の既定は次の構成:

```markdown
## なぜやるか

## きっかけ（一次情報）

## 何ができたら終わりか（完了条件）

## 今回やらないこと・触らないこと

## 任意
（期限・緊急度、却下済み案、受け入れ判定者、実装方針の初期仮説。該当なしなら節ごと省略）
```

## 禁止事項

- 依頼者の確認なしに起票しない
- 意図レベルの答えを依頼者の代わりに創作しない
- 完了条件の無い Issue を起票しない。調査タスクなら「調査結果を◯◯へまとめ、次のアクションを判断できる状態にする」のように完了を観測可能にする
