# polish-issue — Issue を自己完結したプロンプトへ変換する

方針決定・検証という高コストな仕事を、実装時から Issue 時点へ前倒しする。磨かれた本文は、人間にも AI にもそのまま実装の入力になる。判定装置は issue-readiness（質問ゼロテスト）で、本スキルはその判定を通すために足りないものを「調べて・測って・埋める」実行装置。

**issue-readiness との住み分け**: 精査度の判定だけが欲しい（直さなくてよい）なら issue-readiness を単体で使う。本スキルは判定に加えて欠落を埋める修正まで行う。判定を自分でやらず issue-readiness のサブエージェントに委ねるのは、自分が埋めた内容を自分で採点すると欠落を見逃す誘因が生まれるため。

## 非対称規則（このスキルの背骨）

欠落は issue-readiness の A/B/C 分類で扱いを変える:

- **B（設計）・C（機械）レベル** → 自分で埋める。規約・既存コード・過去 PR の調査、実測 PoC、お試し実装で答えを作り、出典付きで本文に書く
- **A（意図）レベル** → 創作しない。正解は起票者の頭の中にしかない。文脈から仮説が立つなら【推測】付きの選択肢として、立たないなら質問として、本文の「要判断」節に載せる
- **出典のない前提** → 【未検証】とし、polish の中で実測して事実化する。実測できないものは【未検証】のまま停止規則に接続する

この非対称を守らないと、もっともらしいが依頼者の意図と違う Issue を自信を持って完成させてしまう。

## ワークフロー

1. **取得と着手判断**: `gh issue view <N> --repo <owner/repo> --json title,body,labels,assignees,comments` で取得する。assignee が付いている、リンクされた PR・ブランチがあるなど人間の着手兆候があれば、磨き上げを中断して報告する（二重作業の防止）
2. **対象リポジトリの特定**: workspace の CLAUDE.md にある役割分担表と Issue 内容から実装先リポジトリを導出し、ローカルクローンを特定する
3. **初回判定**: issue-readiness スキルの分析プロンプトをサブエージェントで実行する
4. **欠落を埋める**:
   - 自答可能な質問 → 出典（path:line、PR/Issue 番号）付きで本文へ反映する
   - 【未検証】 → scratchpad で実測 PoC・お試し実装を行う。仕様が触る実物（ファイル・データ・API 応答）を最低1つ開いて観察する
   - A レベル → 「要判断」節へ。選択肢・根拠・推奨を添え、答えで成果物がどう変わるかを1行付ける
5. **本文草案の組み立て**: 後述の構成で書く。原文は `<details>` で全文保存する
6. **収束判定**: 草案に対して issue-readiness を再実行する。A レベルの残りがすべて「要判断」節に載っていれば収束。載っていない欠落が出たら 4 に戻る（最大2周。収束しない場合は草案と未解決点を報告して終了する）
7. **提示と書き戻し**: 原文からの変更差分サマリと、置いた仮定の一覧を先頭に添えて草案を提示する。依頼者の承認を得てから `gh issue edit` で反映する

### 非対話実行の場合

ループ・スケジュール実行で質問・承認が取れない場合は、書き戻しをせず、草案・差分サマリ・仮定一覧を返して終了する。呼び出し元から指示されている場合のみ、草案のコメント投稿または本文編集を行う。

## 磨き上げ後の本文構成

セクションに所有権を明記する。「人間所有」は実装時に変更不可、「AI 所有」は完了条件を満たす限り実装時の差し替えを許す:

```markdown
## なぜやるか〔人間所有〕

## きっかけ（一次情報）〔人間所有〕

## 何ができたら終わりか（完了条件）〔人間所有〕
検証環境・検証コマンドまで含める。実装ジョブの自己検証手順を兼ねる。

## 今回やらないこと・触らないこと〔人間所有〕

## 前提〔AI 所有〕
出典のあるものだけ事実として書く。【推測】【未検証】のマークは消さない。

## 実装方針〔AI 所有・実装時の差し替え可〕

## 分岐への先回り回答・停止規則〔AI 所有〕
予見できる分岐には先回りで答えを書き、想定外の分岐に遭遇したときは独断で進めず停止して報告する条件を書く。

## 要判断（起票者への質問）
- ◆[Q1] <質問> ／ 選択肢と推奨 ／ 影響: <答えで成果物がどう変わるか>

<details><summary>磨き上げ前の原文</summary>

（原文全文）

</details>
```

## お試し実装の規律

お試し実装は「事実を作る」ための検証であって、実装の先取りではない:

- 実験は scratchpad（または対象ファイルの一時コピー）で行い、対象リポジトリの作業ツリーを変更しない
- 成果はコードではなく事実として本文に還元する。試したコードは破棄し、残す価値のある要点だけを実装方針に書く
- git push・実環境の変更・Issue/PR への書き込み（手順7で承認された書き戻しを除く）をしない
- 実測が権限・安全上できない場合は、その前提を【未検証】のまま停止規則へ接続する

## 完了条件の逆チェック

完了条件を提案・修正したら「この条件を PASS させたまま意図に反する成果物が作れるか」を自問する。無人実行では完了条件そのものが最適化対象になる（Goodhart の法則）ため、人間の実装者相手より一段厳しくする。

## 禁止事項

- 実装に着手しない。お試し実装は検証目的のみで、成果物として提出しない
- A レベルの答えを創作して事実のように本文へ書かない
- 承認なしに Issue 本文・コメントを変更しない
- assignee 付きの Issue を勝手に磨かない
