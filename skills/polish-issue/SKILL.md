# polish-issue — Issue を自己完結したプロンプトへ変換する

方針決定・検証という高コストな仕事を、実装時から Issue 時点へ前倒しする。磨かれたコメントは、人間にも AI にもそのまま実装の入力になる。判定装置は issue-readiness（質問ゼロテスト）で、本スキルはその判定を通すために足りないものを「調べて・測って・埋める」実行装置。

調査と実測を終えたら、結果は対象 Issue へコメントとして投稿する（承認の取り方と非対話実行での例外は手順7と「非対話実行の場合」に従う）。会話の中で報告して終えると、次に Issue を開く人が同じ調査をやり直すことになる。磨き上げの成果物は会話ログではなくコメントであり、投稿して初めてこのスキルは完了する。

**issue-readiness との住み分け**: 精査度の判定だけが欲しい（直さなくてよい）なら issue-readiness を単体で使う。本スキルは判定に加えて欠落を埋める修正まで行う。判定を自分でやらず issue-readiness のサブエージェントに委ねるのは、自分が埋めた内容を自分で採点すると欠落を見逃す誘因が生まれるため。

## 非対称規則（このスキルの背骨）

欠落は issue-readiness の A/B/C 分類で扱いを変える:

- **B（設計）・C（機械）レベル** → 自分で埋める。規約・既存コード・過去 PR の調査、実測 PoC、お試し実装で答えを作り、出典付きでコメントに書く
- **A（意図）レベル** → 創作しない。正解は人間の頭の中にしかないので、まず対話中のユーザーに確認する（後述「A レベルの確認手順」）。回答が得られたら人間所有の節へ反映し、ユーザーにも分からなかったものだけをコメントの「要判断」節に質問として載せる
- **出典のない前提** → 【未検証】とし、polish の中で実測して事実化する。実測できないものは【未検証】のまま停止規則に接続する

この非対称を守らないと、もっともらしいが依頼者の意図と違う Issue を自信を持って完成させてしまう。

## ワークフロー

1. **取得と正本の特定**: `gh issue view <N> --repo <owner/repo> --json title,body,labels,assignees,comments` で取得する。**正本**（磨き上げの入力）は最新の磨き上げコメントとし、それがなければ Issue 本文とする。assignee が付いている、リンクされた PR・ブランチがあるなど人間の着手兆候があれば、磨き上げを中断して報告する（二重作業の防止）
2. **対象リポジトリの特定**: workspace の CLAUDE.md にある役割分担表と Issue 内容から実装先リポジトリを導出し、ローカルクローンを特定する
3. **初回判定**: issue-readiness スキルの分析プロンプトをサブエージェントで実行する。判定対象は正本であることを明示して渡す（本文に古い原文が残るため、指定しないと原文を採点される）
4. **欠落を埋める**:
   - 自答可能な質問 → 出典（path:line、PR/Issue 番号）付きでコメントへ反映する
   - 【未検証】 → scratchpad で実測 PoC・お試し実装を行う。仕様が触る実物（ファイル・データ・API 応答）を最低1つ開いて観察する
   - A レベル → ユーザーに確認する（後述「A レベルの確認手順」）。解けたら人間所有の節へ反映し、解けなかったものだけ「要判断」節へ。選択肢・根拠・推奨を添え、答えで成果物がどう変わるかを1行付ける
5. **コメント草案の組み立て**: 後述の構成で書く。原文は Issue 本文に残り続けるので、草案に複製しない
6. **収束判定**: 草案に対して issue-readiness を再実行する。ユーザー確認で解けなかった A レベルがすべて「要判断」節に載っていれば収束。載っていない欠落が出たら 4 に戻る（最大2周。収束しない場合は草案と未解決点を報告して終了する）
7. **提示と投稿**: 原文からの変更差分サマリと、置いた仮定の一覧を先頭に添えて草案を提示する。依頼者の承認を得てから `gh issue comment <N> --repo <owner/repo> --body-file <草案ファイル>` で投稿する。Issue 本文（最初のコメント）は編集しない。正本が既に磨き上げコメントの場合も、本文ではなく新しいコメントを投稿し、冒頭で以前の磨き上げコメントを置き換える旨を書く（正本は常に最新コメント1つ）

### A レベル（意図）の確認手順

A レベルの欠落は、いま対話しているユーザーに聞けばその場で解ける。Issue に質問を書いて起票者の返信を待つのは、磨き上げの完了を数日単位で遅らせるうえ、返信が来なければ Issue が質問だらけのまま放置される。**Issue への質問は最後の手段**とし、まずユーザーに確認する。

1. A レベルの欠落をまとめ、AskUserQuestion で確認する（1回最大4問）。選択肢には文脈から立てた【推測】仮説と「分からない（起票者に聞く）」を用意し、選ぶだけで答えられるようにする
2. 回答が得られた項目は、人間所有の節（目的・きっかけ・完了条件・対象外）へ反映する。出典として「対話で確認」と書き、Issue 原文由来の記述と区別できるようにする
3. ユーザーが「分からない」「起票者の判断」と答えた項目だけを「要判断」節に質問として残す
4. 手順7の差分サマリでは、対話で確認して埋めた項目と、Issue に質問として残した項目を分けて示す

ユーザーが起票者本人でない場合も、回答は人間の判断として採用してよい。ただし出典を「対話で確認」と明記し、起票者が後から訂正できる状態にしておく。

### 非対話実行の場合

ループ・スケジュール実行で質問・承認が取れない場合は、投稿をせず、草案・差分サマリ・仮定一覧を返して終了する。呼び出し元から指示されている場合のみ、草案をコメントとして投稿する。A レベルの確認も取れないため、A レベルの欠落はすべて「要判断」節に質問として残す。

## 磨き上げ後のコメント構成

冒頭で、実装の入力がこのコメントであることを宣言する。Issue 本文は起票時の原文として残るため、どちらが正本か読み手に迷わせないための1行。

セクションに所有権を明記する。「人間所有」は実装時に変更不可、「AI 所有」は完了条件を満たす限り実装時の差し替えを許す。人間所有の節は原文の意図と対話で確認した回答だけを書き、変更した点は手順7の差分サマリで示す:

```markdown
**実装の入力はこのコメント**（Issue 本文は起票時の原文として保持）

## 目的〔人間所有〕

## きっかけ（一次情報）〔人間所有〕

## 完了条件〔人間所有〕
検証環境・検証コマンドまで含める。実装ジョブの自己検証手順を兼ねる。

## 対象外〔人間所有〕

## 前提〔AI 所有〕
出典のあるものだけ事実として書く。【推測】【未検証】のマークは消さない。

## 実装方針〔AI 所有・実装時の差し替え可〕

## 分岐への先回り回答・停止規則〔AI 所有〕
予見できる分岐には先回りで答えを書き、想定外の分岐に遭遇したときは独断で進めず停止して報告する条件を書く。

## 要判断（起票者への質問）
ユーザーに確認しても解けなかった意図だけを載せる。残らなければ節ごと省略する。
- ◆[Q1] <質問> ／ 選択肢と推奨 ／ 影響: <答えで成果物がどう変わるか>

<details><summary>お試し実装・PoC のコード（検証用。実装の入力ではない）</summary>

- 確認したこと: <何を確かめたか>
- 実行方法: <コマンド>
- 観察結果: <出力・計測値>

（試したコード）

</details>
```

## お試し実装の規律

お試し実装は「事実を作る」ための検証であって、実装の先取りではない:

- 実験は scratchpad（または対象ファイルの一時コピー）で行い、対象リポジトリの作業ツリーを変更しない
- 成果はコードではなく事実としてコメントに還元する。残す価値のある要点は実装方針に書き、試したコード自体はコメント末尾の `<details>` に折りたたんで残す（再現用の実行コマンドと観察結果を添える）
- git push・実環境の変更・Issue/PR への書き込み（手順7で承認されたコメント投稿を除く）をしない
- 実測が権限・安全上できない場合は、その前提を【未検証】のまま停止規則へ接続する

## 完了条件の逆チェック

完了条件を提案・修正したら「この条件を PASS させたまま意図に反する成果物が作れるか」を自問する。無人実行では完了条件そのものが最適化対象になる（Goodhart の法則）ため、人間の実装者相手より一段厳しくする。

## 禁止事項

- 実装に着手しない。お試し実装は検証目的のみで、成果物として提出しない（折りたたみに残すのは検証記録としてであり、そのまま採用させるためではない）
- A レベルの答えを創作して事実のようにコメントへ書かない
- A レベルの欠落をユーザーに確認せず、いきなり Issue への質問にしない（非対話実行を除く）
- 承認なしに Issue へコメントを投稿しない。Issue 本文（最初のコメント）は承認があっても編集しない
- 調査結果を会話の報告だけで終わらせない。対話できる場合は承認を得たうえで、必ず対象 Issue にコメントとして残す
- assignee 付きの Issue を勝手に磨かない
