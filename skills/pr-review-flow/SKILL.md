# pr-review-flow — PR レビュー統合フロー

PR レビューを (1) 最新コードの同期 → (2) 多観点レビュー → (3) 状況に応じた出力 の順で回す。
このスキルは既存の専門スキルを束ねるオーケストレーターである。レビュー判定そのものは各スキルに委ね、ここの責務は「最新コードに対して」「複数観点を漏れなく」「適切な出力で」回すことに絞る。

## なぜこのフローか

- **stale なローカルでのレビューは害になる。** 既に直っている箇所を指摘したり、最新の変更を見落とす。だから最初に必ず最新を取得する。
- **観点は一つのレビューアでは漏れる。** `pr-review-toolkit:review-pr` は変更内容に応じて専門エージェント（正確性・簡素化・型・テスト・サイレント障害・コメント）を起動し、1回で観点を網羅する。コード観点の網羅はこのスキルに任せ、同種のレビューアを重ねない。文章規範の `japanese-tech-writing` は別軸の観点なので、review-pr と併用しても重複しない。
- **説明と実装のずれは、コード観点のレビューでは出ない。** review-pr の各エージェントはいずれも diff の内側だけを判定材料にするため、レビューイが書いた説明と実装が食い違っていても検出されない。レビューイの理解そのものは観測できないが、説明と実装の差なら観測できる。差が出た箇所が、認識を合わせる会話の議題になる。
- **出力は状況で変わる。** 共有して相談したいだけ、PR に残したい、その場で直したい、はそれぞれ別の操作。固定せず選ぶ。
- **同期が不要ならこのフローは使わない。** レビュー対象が既に手元の作業ツリーにある（コミット前の自分の変更など）なら、このフローの同期層は要らない。軽く一読するだけなら `code-review` スキル、多観点で見たいが同期が不要なら `pr-review-toolkit:review-pr` 単体で足りる。このフローの価値は同期層と出力層にある。その場合も、ドキュメント差分には `japanese-tech-writing` を併用する。

## 1. 入力と出力意図の特定

対象 PR を特定する。URL、`owner/repo#番号`、PR 番号のいずれか。指定がなければユーザーに確認する。

`gh pr view <ref> --json title,body,headRepository,headRefName,baseRefName,headRefOid,files,isCrossRepository` で、タイトル・本文・対象リポジトリ名・head ブランチ・base ブランチ・head の SHA・変更ファイル・fork からの PR かを把握する。変更ファイルの種類（コード中心かドキュメント中心か）は後段の観点選択に使う。タイトルと本文はレビューイが書いた説明であり、手順3の照合に使う。

`gh` は cwd の git remote から対象リポジトリを解決するため、cwd が対象リポジトリの外だと PR 番号だけでは失敗する。番号だけで指定されたときは `-R <owner>/<repo>` を付ける。

依頼文から出力意図を読み取る。「レビューして」なら要約（モード a）、「コメントして」ならインライン投稿（モード b）、「直して」「反映して」なら修正反映（モード c）。判別できなければ既定で a とし、b・c も選べることを伝える。

## 2. 最新コードの同期

レビューは必ず「今リモートにある最新の PR コード」に対して行う。ローカルが古いまま進めない。

- 対象リポジトリのローカルパスを特定する。通常は `~/workspace/<リポジトリ名>`。無ければユーザーに場所を確認する。
- PR の head を取得する: `git fetch origin pull/<N>/head`。
- **レビュー用に worktree を切るのを既定とする**: `git worktree add --detach <作業用パス> <headRefOid>`。ローカルの現在ブランチや未コミット・未追跡ファイルを汚さず、PR の実コードだけを対象にできる。ローカルに同名の未追跡ファイルがあると `gh pr checkout` は衝突しうるため、worktree が安全。worktree を使えない事情があるときだけ `gh pr checkout <ref>` を使う。
  FETCH_HEAD でなく headRefOid を直接指定するのは、`gh pr view` で取得したメタデータ（files 一覧・差分範囲）と同じコミットをレビューするためである。FETCH_HEAD は他の fetch で上書きされうる可変の参照だが、headRefOid は不変のコミット ID なので、メタデータを取った時点の head に決定論的にピン留めできる。add が失敗するのは、その OID のコミットがローカルに無いとき、つまり `gh pr view` と fetch の間に PR が force-push されたときである。再 fetch しても旧 OID は取れないので、`gh pr view` から headRefOid を取り直して fetch → add をやり直す。これが保証するのは「最新の head」ではなく、files 一覧や差分範囲と同一の SHA を一貫してレビューすることである。
- **submodule を使うリポジトリ**（environment-config や cas-tf-modules を参照する構成など）では、worktree 内で `git submodule update --init --recursive` を実行して submodule も最新の参照に合わせる。これを怠ると、参照先モジュールの変更を含む PR を正しく読めない。
- レビュー対象の差分範囲を確定する: `git fetch origin <baseRefName>` の後、`git diff origin/<baseRefName>...HEAD --stat` の変更ファイル一覧が `gh pr view` の files と一致することを確認する。worktree は checkout 直後で作業ツリーに差分が無いため、`git diff` 単体では変更を特定できない。
- レビュー完了後は `git worktree remove <作業用パス>` で後片付けする。モード c で修正した場合は push 済みであることを確認してから消す。push していないコミットは worktree を消すと参照が失われる。

## 3. 意図の復元と照合

レビューイが書いた説明と実装が食い違っていないかを見るために、**差分だけを根拠にした意図の記述**をサブエージェントに作らせ、手順1で取得した説明と突き合わせる。

差分が小さく意図が自明な PR では省いてよい。submodule pointer の更新、依存バージョンの引き上げ、typo 修正などは、復元するまでもなく読める。

**復元するサブエージェントに、PR 番号・URL・タイトル・説明・ブランチ名を渡さない。** 説明を先に読ませると、モデルはその説明どおりに差分を解釈するため、復元が独立した観測にならず、突き合わせても差が出ない。番号を渡さなければ `gh pr view` を実行できないので、指示だけに頼らず構造として遮断できる。

コミットメッセージも作者による自己申告なので、同じ理由で渡さない。ここは経路が残りやすい。手順2で同期した worktree は PR の head にあるため、`git log` を叩けばコミットメッセージに到達できてしまう。渡すものを次のように分ける。

- **差分**: `git diff origin/<baseRefName>...HEAD > <差分ファイル>` でファイルに落とし、そのパスを渡す
- **周辺コード**: base のツリーを `git archive origin/<baseRefName> | tar -x -C <展開先>` で展開して渡す。git のメタデータを持たないただのディレクトリになるので、`git log`・`git branch`・`git show` から到達する経路がまとめて閉じる
- **ファイル名に PR 番号を入れない**。`pr-343.diff` のような名前は、それ自体が番号を漏らす

worktree を渡す形では遮断しきれない。base に切っても `git branch -a` には作者のブランチ名が並び、そこには目的だけでなくレビュー往復の回数（`work/....-comments-r4` のような命名）まで表れる。`git log --all` を叩けば全ブランチのコミット件名にも届く。復元するモデルは「GitHub を検索しない」という指示には従うが、手元の git 履歴を同じ経路とは認識しない。だから指示ではなくツリーの側で閉じる。

`git archive` の展開先は base 時点の内容なので、差分が参照する他ファイルの存在確認（リンク先の文書があるか、呼び出し元がどこか）はそのまま行える。origin から取るため、ローカルのブランチが古くても影響を受けない。

サブエージェントが使えない場合は、説明を読む前に差分だけを読んで復元を書き、そのあとで説明を参照する。順序で独立性を作る形になるが、会話の文脈から意図を知っている可能性が残るため、サブエージェントより弱い。その旨を出力に添える。

### 復元プロンプト（サブエージェントに渡すテンプレート）

`{ }` を埋めてそのまま渡す。プロンプトは自己完結しており、このスキル本文や会話の知識を前提にしない。

```text
あなたはコードレビュアーです。差分だけを読んで、この変更が何をしようとしているかを
復元してください。修正は行いません。

## 対象
- 差分: {差分ファイルのパス}
- 周辺コード: {展開先のパス}（base 時点のツリー。変更後のコードは含まない）

差分の作者による説明（PR 本文、コミットメッセージ、ブランチ名、Issue）は意図的に
渡していません。GitHub 上で該当の PR や Issue を検索して探しにいかないでください。
差分と周辺コードだけを根拠にしてください。
説明を知らないまま読むことが、この作業の目的です。

## 出力

### この変更が達成しようとしていること
3行以内。差分全体を貫く目的を書く。

### 変更の単位ごとの内訳
まとまりごとに「何を変えたか」と「なぜそうしたと読めるか」を書き、`file:line` を添える。
なぜの部分が差分から一意に決まらないときは【推測】と付ける。

### 差分だけでは意図が読み取れなかった箇所
なぜ読み取れないか（判断の根拠が差分の外にある、選択肢が複数あって決まらない、など）
を一行添える。無理に埋めない。

### 影響範囲
差分に現れていないが影響を受ける箇所。変更された関数やコマンドの呼び出し元、
同じ設定値を参照している箇所などを、周辺コードを読んで分かる範囲で挙げる。
確認にリポジトリ外の情報が要るものは【未検証】と付ける。

### 作者の言葉が目に入ったか
作業中に、作者による説明（コミットメッセージ、ブランチ名、Issue、PR 本文）が
目に入ったかを報告する。入った場合は経路と、復元のどの記述に影響した可能性が
あるかを添える。入らなかった場合は「なし」と書く。
```

最後の節は、遮断が実際に効いたかを確認するためのもの。ここに報告が上がったときは、その項目を照合結果から割り引いて扱う。

### 突き合わせ

復元が返ったら説明と比べ、説明にあって実装に無いもの、実装にあって説明に無いもの、双方にあるが解釈が食い違うものに分ける。

説明が空、または「対応しました」程度で内容が無いときは、突き合わせる対象が存在しない。復元をそのまま提示し、説明が無いことを結果として伝える。説明の無い PR は認識のずれが最も起きやすいので、黙って省略しない。

**不在を主張するときは、探した範囲を書く。** 「説明にあって実装に無い」は、こちらが見落としただけという偽陽性が最も出やすい。根拠が不在で `file:line` を書けないぶん、どこを確認したうえで見当たらないと言っているのかを添える。読み手が数秒で棄却できるかどうかが、この出力の使い勝手を決める。

## 4. レビュー実行

- **PR の内容にかかわらず `pr-review-toolkit:review-pr` を実行する。** 変更内容に応じて専門エージェントが起動し、観点を網羅する。ドキュメントのみの PR でも `code-reviewer`（正確性・品質・CLAUDE.md 準拠）と `comment-analyzer`（記述の正確性・整合）は有効なので、省略しない。
  - `code-reviewer` — 正確性・品質・CLAUDE.md 準拠（常時）
  - `code-simplifier` — 簡素化・可読性（レビュー通過後）
  - `pr-test-analyzer` — テスト網羅（テスト変更時）
  - `silent-failure-hunter` — 握りつぶし・サイレント障害（エラー処理変更時）
  - `type-design-analyzer` — 型設計（型の追加・変更時）
  - `comment-analyzer` — コメント整合（コメント・ドキュメント追加時）

  review-pr 起動時は、対象コードが worktree（`<作業用パス>`）にあり、レビュー範囲が `origin/<baseRefName>...HEAD` の差分であることを明示する。review-pr は既定で cwd の作業ツリー `git diff` から変更ファイルを特定する。同期済み worktree は checkout 直後で差分が無いため、この明示を欠くと「変更なし」と誤認する。
- **ドキュメント差分を含む場合**（Markdown、設計書、構築手順書など）: 上記 review-pr に加えて `japanese-tech-writing` スキルの文章規範でもレビューする。review-pr を置き換えるのではなく、文章面の観点として重ねる。
- 各指摘には根拠を `file:line` で添える。同期した最新コードの実際の行を指す。

## 5. 出力の選択

依頼に出力の指定があればそれに従う。無ければ既定で a を返し、b・c も選べることを伝える。

- **a. 要約レポートを会話に返す**: 手順3の照合結果と review-pr の結果を次の構成で日本語にまとめて提示する。PR には書き込まない。
  - 説明と実装のずれ: 説明にあって実装に無いもの（探した範囲を添える）/ 実装にあって説明に無いもの `file:line` / 解釈が食い違うもの
  - 読む前に知っておくこと: 差分だけでは意図が読み取れなかった箇所 / 差分に現れていない影響範囲
  - 判定: マージ可否の目安（重大な問題の有無）
  - 重大（must-fix）: `観点名` `file:line` — 問題 / 提案
  - 重要・提案: 同形式で重大度順に
  各指摘に観点名（どの agent が出したか）と `file:line` を必ず添える。差分から一意に決まらない解釈は【推測】、確認にリポジトリ外の情報が要るものは【未検証】と付ける。
  「読む前に知っておくこと」はずれの有無にかかわらず出す。ずれが検出されなかった PR でも、差分に映らない影響範囲を先に知っているかどうかで、同じ時間で気付ける量が変わる。
- **b. PR にインラインコメントを投稿する**: a の指摘を該当行にコメントする。`gh pr comment` と `gh pr review` は行単位のコメントに対応していないため `gh api` を使い、Reviews API で全指摘を 1 レビューにまとめて投稿する。指摘ごとの単発投稿（`POST .../pulls/<N>/comments`）は通知が指摘の数だけ飛び、途中で失敗すると中途半端に残る:

  ```
  gh api repos/<owner>/<repo>/pulls/<N>/reviews --input - <<'EOF'
  {"commit_id": "<headRefOid>", "event": "COMMENT", "body": "<総評>",
   "comments": [
     {"path": "<ファイル>", "line": <行番号>, "side": "RIGHT", "body": "<指摘>"}
   ]}
  EOF
  ```

  削除された行への指摘は `side` を `LEFT` にする。Reviews API は diff のハンクに現れる行にしかコメントできず、ハンク外の行に付けると 422 で失敗する。ハンクに含まれない行や変更していないファイルへの指摘は `gh pr comment` の全体コメントにまとめる。投稿は外向きの操作なので、内容を提示して確認を取ってから実行する。
  手順3の照合結果は、そのまま投稿しない。ずれの指摘は相手が書いた説明への指摘であり、復元が誤っていたときの棄却コストをレビューイに転嫁することになる。議題にすべきものはレビュワーが判断し、自分の言葉で書く。
- **c. コードに修正を反映する**: review-pr の指摘のうち明確な修正（バグ修正・簡素化など）を worktree に適用する。適用範囲を提示して確認を取ってから、小さくこまめにコミットする。意図レベルの判断が要る修正（仕様の解釈が分かれるもの）は勝手に入れず、指摘として残す。
  worktree は detached HEAD のため、コミットしただけでは PR に反映されない。`git push origin HEAD:<headRefName>` で PR ブランチへ push するところまで行う。push 後は修正した観点だけ review-pr を再実行し、指摘が解消したことを確認する。fork からの PR（isCrossRepository が true）は origin へ push できないため、修正は適用せず指摘として返す。

## 原則

- 最新コードに対してレビューする。同期を飛ばさない。
- レビュー判定は各専門スキルに委ね、このフローは束ねることに徹する。重複してレビュー観点を再実装しない。
- 意図を復元するサブエージェントに、作者による説明を渡さない。独立していない復元は突き合わせる意味がない。
- ずれを見つけても、どちらが誤っているかは判定しない。説明が足りないのか実装が外れているのかは、レビュワーとレビューイの会話で決まる。
- 外向きの投稿（b）と破壊的な修正（c）は、実行前に必ず確認を取る。
- 出典のない指摘を断定しない。`file:line` か PR 上の根拠を添える。
